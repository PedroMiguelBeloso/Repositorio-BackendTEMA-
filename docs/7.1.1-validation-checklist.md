# 7.1.1 — Validation checklist

## Sources of truth

This implementation was checked against the supplied functional specification, functional proposal, OpenAPI contract, reviewed DBML, backend architecture, and package/class diagram. The functional specification says M1 is the source of truth for expected evidence and restricts M2 verification to Start Up, Take Over, and Soporte y Software Factory. The architecture requires a modular monolith with API, application, domain and infrastructure boundaries; `verification` consumes public readers from `process` and `service` and does not access their private JDBC tables.

## Domain rule placement

Local invariants are enforced in domain constructors/factories/methods. Rules needing multiple expectations are handled by `TicketSelectionPlanner`. Rules needing M1 reads, scope resolution and catalog integrity checks are handled by `VerificationContextLoader`. HTTP validation and error translation remain in `verification.api`. Domain code has no Spring, HTTP, DTO or JDBC dependency.

## External services and persistence

The preview/context use cases do not call Drive, Redmine, GPT or a run repository. They do not create a verification run or a ticket selection record. No Flyway migration was added for context loading. The OpenAPI YAML referred to by the task was absent from this checkout, so the existing preview response shape was retained.

## Validation

Run the Maven compile and test suite with Java 21. Database integration tests use Testcontainers and require Docker.
