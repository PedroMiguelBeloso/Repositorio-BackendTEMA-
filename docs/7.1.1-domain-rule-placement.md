# 7.1.1 — Ubicación de reglas de dominio

## Criterio

El modelo de dominio protege sus invariantes locales mediante constructores y operaciones con nombre de negocio. Los servicios de aplicación coordinan lectores/repositorios y aplican reglas que requieren consultar más de un objeto o una fuente de verdad. La API valida la forma HTTP y traduce errores a `ProblemDetail`. El dominio no depende de Spring, HTTP, DTO ni `JdbcTemplate`.

## Reglas y ubicación

| Regla | Ubicación | Motivo |
|---|---|---|
| `MACRO_ACTIVITY` requiere `macroActivityId`; `PROCESS` lo prohíbe | `verification.domain.VerificationTarget` | Es una invariante interna del objeto objetivo; no necesita consultar otros objetos. |
| `PROCESS` no puede llevar `macroActivityId` y `MACRO_ACTIVITY` sí | `VerificationTarget` | La combinación scope/ID debe ser válida antes de entrar al caso de uso. |
| Una expectativa de preview conserva location/activityId válidos | `verification.domain.PreviewExpectation` | La consistencia de la proyección pertenece al objeto que se entrega al siguiente caso de uso. |
| Toda expectativa TICKET del preview debe quedar asociada a un grupo | `PreviewExpectation` | Evita un preview internamente inconsistente. |
| Grupo con ID, macroactividad, cardinalidad y relaciones válidas | `TicketSelectionGroup` | Son invariantes propias del grupo. |
| Una sola entrada TICKET por macroactividad | `TicketSelectionPlanner` + `MacroActivity.ticketInputs()` | La regla depende del conjunto de expectativas de una macroactividad; por eso es un servicio de dominio y no una propiedad aislada. |
| Todas las expectativas TICKET de una macroactividad comparten cardinalidad | `TicketSelectionPlanner` | Requiere comparar varias expectativas, por lo que no pertenece a una sola expectativa. |
| Un único grupo por macroactividad y lista de expectativas relacionadas | `TicketSelectionPlanner` | La construcción depende de varias expectativas y de la macroactividad completa. |
| ID estable del grupo | `TicketSelectionGroup.forMacroActivity` / `stableIdFor` | Es una propiedad del objeto de dominio derivada de su macroactividad publicada. |
| Entradas → registros ordenados por actividad → salidas | `MacroActivity.expectationsInVerificationOrder()` | La macroactividad posee la estructura y la semántica de orden del proceso. |
| Versión publicada como estado del proceso | `process.domain.ProcessVersion.isPublished()` | Es un hecho del agregado `ProcessVersion`; la capa de aplicación solo lo consulta. |
| Proceso habilitable para M2 | `process.domain.ProcessCode.isM2Enabled()` / `ProcessDefinition.isVerifiable()` | La disponibilidad M2 está determinada por el código del proceso y ya es una regla del dominio M1. |
| Servicio existente, asignación exacta al servicio y proceso M2 habilitado | `VerificationContextLoader` | Requiere consultar `service` y `process`; son reglas de aplicación entre agregados/lectores. |
| `PROCESS` incluye todas las macroactividades; `MACRO_ACTIVITY` solo la seleccionada | `VerificationContextLoader` | Necesita la versión publicada y el ID solicitado. |
| Contexto inmutable con servicio, versión, alcance y expectativas resueltas | `verification.domain.VerificationContext` | Es una proyección en memoria compartida por preview e inicio futuro; no es un snapshot persistido. |
| Registro de catálogo existente y nomenclatura para `DOCUMENT`/`FOLDER` | `VerificationContextLoader` + lectura por lote del catálogo | Detecta configuraciones publicadas inconsistentes antes de devolver el contexto. |
| Expectativas con registro compartido preservan IDs, ubicación y orden | `VerificationContextLoader` | Cada expectativa se proyecta por separado; el catálogo se lee una vez por lote. |
| Error funcional HTTP 4xx | `verification.api.VerificationApiExceptionHandler` | Traduce una excepción de dominio a `ProblemDetail` sin contaminar el dominio con Spring. |
| Sin efectos persistentes ni fuentes externas en preview/contexto | `VerificationPreviewService` + `VerificationContextLoader` | El caso de uso solo lee los límites de M1 y construye un resultado. |

## Base de datos y concurrencia

El contexto no introduce escrituras ni estados nuevos, por lo que no necesita una migración específica. La versión se lee por ID exacto y las fuentes externas ausentes se representan sin inventar identificadores. El futuro `POST /verifications` deberá reutilizar el loader y volver a validar la revisión del servicio antes de persistir un run.
